# Phase 3 hardware constraints

This document captures environment, SDK, hardware, and software constraints
that apply across all Phase 3 tasks (3.0.5b, 3.1, 3.2, 3.3, and beyond).
It is not Phase 3.1-specific.

---

## Environment

```
Python:      .venv\Scripts\python.exe  (repository root)
PYTHONPATH:  <repo_root>               (required for task module imports)
PowerShell:  Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
Config:      . .\env.local.ps1         (load local env into current session)
```

### Long-running tasks

All hardware captures must be launched with `Start-Process -NoNewWindow`
to detach from the terminal.  The terminal times out and kills child
processes after 2 minutes by default.

```powershell
Start-Process -FilePath ".venv\Scripts\python.exe" `
  -ArgumentList "scripts/capture_xxx.py --hardware ..." -NoNewWindow
```

The read-only monitor must be launched independently in a separate process:

```powershell
Start-Process -FilePath ".venv\Scripts\python.exe" `
  -ArgumentList "scripts/monitor_run_status.py --status-dir ..." -NoNewWindow
```

Do not chain task and monitor in the same command line — monitor is a
persistent GUI that should survive task completion.

## Hardware constraints

### H1: LCD settle time

`lcd.settle_ms` must be **at least 200 ms** for all Phase 3 tasks.
2 ms is insufficient for the LCD liquid-crystal elements to physically
switch; the camera captures LCD transition frames, corrupting bright/dark
references and producing unreliable bar scan energies.

Experienced in Phase 3.1: settle_ms=2 caused bright_sum ≈ dark_sum
(difference only 0.09% of total frame energy).  settle_ms=200 gave
proper bright-dark contrast.

Applies to: all tasks that call `lcd_service.show_mono_mask()` in a
loop over masks.

### H2: LCD subpixel axis

`subpixel_axis` must match the `reported_shape` returned by the LCD
backend.  On current hardware, pygame reports `(2560, 540, 3)` —
height=2560, width=540.  The 540-pixel edge (to be tripled) is the
width dimension, so `subpixel_axis = 1`.

- axis=0: physical = `[3H, W]`
- axis=1: physical = `[H, 3W]`

Do not guess.  The LCD plan YAML must declare `lcd.subpixel_axis`
explicitly, and the CLI must pass `--lcd-subpixel-axis`.

### H3: TLS wavelength filtering

The Xe lamp outputs broadband white light.  Without TLS monochromator
filtering, the camera overexposes with PSF-safe parameters (which assume
filtered monochromatic light).

Phase 3 tasks must enforce TLS participation by default:
- Pass `--tls-serial` or set `TLS_C1_SERIAL`.
- The dangerous `--allow-wavelength-labels-without-tls` override is
  reserved for explicit manual external wavelength control.

Applies to: 3.1, 3.2a, 3.2b, 3.3, 3.4+.

### H4: Xe lamp warm-up drift

The Xe lamp output drifts significantly during the first ~10 minutes
after ignition.  A single-pass bar scan (X then Y) spans ~10 minutes
and will show a strong linear trend in energies (observed ~150k drop).

Mitigations:
- Wait for the lamp to thermally stabilise before starting the scan
  (warm-up time depends on lamp model; consult the lamp manual).
- If a linear trend persists, the bar scan fit algorithm's baseline
  subtraction compensates partially.
- For very long scans, consider splitting into shorter segments or
  using periodic bright-reference re-measurement.

### H5: Bar scan initial position artifact

The first 1-3 bar scan positions may contain an outlier from LCD
initialisation (black → white transition residue).  This is a single
isolated data point — clean it by replacing with the average of
neighbouring positions, not by deleting the HDF5.

Do not remove the entire dataset because of one outlier.

## Software constraints

### S1: Never delete HDF5 files

Raw capture HDF5 files are experimental evidence — the sole auditable
record of every hardware run.  Hardware is slow; data cannot be
regenerated by re-running code.

- Corrupted/contaminated HDF5 must be **renamed** with a descriptive
  suffix (e.g. `_lamp_drift`, `_y_contaminated`), never deleted.
- Before deleting any HDF5, confirm it is a duplicate, corrupted beyond
  recovery, or explicitly superseded by a documented re-run whose output
  has been validated.

### S2: Bar scan data must be flushed + backed up before fit

The bar scan takes ~10 minutes.  The circle profile fit runs
immediately after and can crash.  If bar scan data is only in HDF5
(not yet closed), a fit crash may corrupt the file and lose all data.

Implementation requirement:
1. After bar scan completes, call `writer.flush()` and save positions
   and energies as `.npy` files.
2. Only then proceed to `solve_aperture_from_profiles`.

The `.npy` backup is atomic (small files), providing a secondary
recovery path if the HDF5 is corrupted.

### S3: Energy metric uses abs() — no invert, no sign debates

```python
energy = float(abs(bright_sum - np.sum(frame)))   # bar scan
energy = float(abs(np.sum(frame) - dark_sum))     # radius scan
```

Do not add `invert` parameters, linear detrend, or per-configuration
sign selection.  The physics of whether a dark bar increases or
decreases camera signal is handled by `abs()`.

### S4: Resume must use a separate output HDF5

`--resume-from-h5` loads bar scan data from a source HDF5.  The
`PupilGeometryWriter` opens a new output file with `"w"` (truncate)
mode.  The source and output **must be different paths** — otherwise
the writer truncates the source before the resume code reads it.

Current implementation: output path gets `_resumed` suffix
(e.g. `bishe_pupil_geometry.h5` → `bishe_pupil_geometry_resumed.h5`).

### S5: Camera parameters from 3.0.5b per-gain table

`camera_params_psf_safe.json` exposes `per_gain_safe_params` with
gain-keyed safe exposure upper bounds.  Tasks should select a gain
via plan field `camera_gain_selection` rather than hardcoding
exposure_us / gain_db.

Phase 3.1 used `camera_gain_selection: "10.0"` (gain=10 dB,
exposure=540 us, PSF-safe across all tested wavelengths).

### S6: Provenance chain

Every output must record:
- `source_raw_capture_h5`
- `pupil_window_source` (from Phase 3.1)
- `camera_params_source` (from Phase 3.0.5b)
- `psf_roi_source` (from Phase 3.2a, if applicable)

### S7: Resumed HDF5 must be self-contained

When `--resume-from-h5` is used, the writer's output HDF5 must
contain **all** data needed for reproducibility:
- Bar scan data (copied from source HDF5)
- Bright/dark references (newly captured in current run)
- Radius scan data (newly captured)
- Metadata (plan, LCD, camera, TLS)

The resumed HDF5 is the canonical experimental record for that run.
Downstream scripts (`analyze_pupil_geometry.py`) must be able to read
only the resumed HDF5 without consulting the source HDF5.

### S8: Bright/dark references in resume mode

When resuming, newly captured bright and dark reference frames are
written to the resumed HDF5.  The radius scan uses the **current run's**
`dark_sum` (from the fresh dark reference).  Do not override
`bright_sum` or `dark_sum` with values loaded from the source HDF5.

The source HDF5's `bright_sum` / `dark_sum` were used only for the
bar scan energy computation at the time of original acquisition.  The
resumed radius scan is a new acquisition and uses its own references.

## Phase 3.2 specific

### P1: Coordinate systems

- `effective_pupil_window.json` (Phase 3.1) is in **LCD physical coordinates**.
- `psf_roi.json` (Phase 3.2a) is in **camera sensor coordinates**.

These are different coordinate systems.  Do not conflate them.
Both must be recorded as provenance in downstream HDF5 files.

### P2: LCD mask for PSF capture

When capturing PSFs (3.2a, 3.2b, 3.3, 3.4+), the LCD must display
`effective_pupil_window`: inside the circular window = all-open
(transmissive), outside = all-closed.  This isolates the light path
to the calibrated pupil region.

### P3: psf_roi.json is single source of truth

All PSF crops (repeatability, dOTF, PSF dictionary) must use the
same `psf_roi.json`.  Do not re-derive the crop per script.
