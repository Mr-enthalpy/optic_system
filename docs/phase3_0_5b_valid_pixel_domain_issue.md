# Phase 3.0.5b valid-pixel domain issue

## Problem

Phase 3.0.5b currently evaluates PSF safety as:

```text
all raw burst frame pixels strict < frame_dtype_full_scale
```

That rule is correct for valid imaging pixels, but recent hardware probes show
that applying it to the full camera frame is confounded by unstable top-row
pixels. Short shutter settings can intermittently produce near/full-scale
pixels at `y=0`, while the rest of the frame remains far below full scale.
This can make calibration fail because of a camera artifact rather than real
PSF saturation.

## Hardware Evidence

Environment:

- Branch: `phase3-bishe-experimental-loop`
- Camera: `15471217`, RAW8, frame shape `[2048, 2448]`
- LCD: display index `1`, `subpixel_axis=1`
- LCD was explicitly reset to all-transmissive before the confirming probe.
- TLS: fixed at `550.0 nm`, grating `1`
- Full scale source: frame metadata format `raw8 -> 255`
- The confirming probe kept Windows display/system awake to avoid LCD blackout.

Local probe artifacts were generated but are not committed:

```text
outputs/diagnostics/shutter_gain_peak_probe/probe_awake_20260515_003644.csv
outputs/diagnostics/shutter_gain_peak_probe/probe_awake_20260515_003644.json
```

Representative results at `gain=0 dB`:

```text
50 us:
  all-frame peak at y=0
  after dropping row 0: peak ~= 38..40, no full-scale pixels

100 us:
  one repeat all=255@(0,7)
  after dropping row 0: peak ~= 38..41, no full-scale pixels

500 us:
  one repeat all=255@(0,7)
  after dropping row 0: peak ~= 59..62, no full-scale pixels

1000 us:
  one repeat all=255@(0,7)
  after dropping row 0: peak ~= 85..102, no full-scale pixels

2000 us:
  all-frame peaks still at y=0
  after dropping row 0: peak ~= 150..164, no full-scale pixels

4000 us:
  real PSF region begins saturating near (y ~= 909, x ~= 1171)
  repeated bursts contain 57..406 full-scale pixels after dropping row 0

6288.8 us and above:
  real PSF region has many full-scale pixels

50000 us:
  real PSF region has more than 11000 full-scale pixels in repeated bursts
```

This suggests two distinct effects:

1. Short-shutter full-scale events are dominated by top-row artifacts or
   invalid pixels.
2. Longer-shutter saturation is real optical PSF-region saturation.

## Why This Matters

The current binary search assumes the safety predicate is meaningful over the
evaluated domain. If that domain includes invalid top-row artifacts, then:

- `exposure_min` can fail even when the optical PSF is not saturated.
- A canonical `camera_params_psf_safe.json` can be blocked by camera artifacts.
- The assumption that lower shutter is safer is not sufficient unless the
  safety predicate excludes invalid camera pixels or explicitly models artifact
  behavior.

Separately, if `R` is manually reduced to a low upper bound such as `500 us`,
and `R` is safe, the current binary-search short-circuit is expected. `R` is
the maximum allowed exposure inside that search interval. That behavior is not
itself the bug. The issue is the unvalidated full-frame safety domain.

## Proposed Direction

Do not weaken the strict PSF safety rule globally. Instead, add an explicit and
auditable valid-pixel domain before running canonical Phase 3.0.5b:

```text
PSF-safe = all raw burst frame pixels within valid_camera_pixel_mask
           strict < frame_dtype_full_scale
```

Candidate implementation options:

- Add a `valid_camera_pixel_mask` or `camera_valid_roi` artifact generated by a
  small hardware diagnostic.
- At minimum, support excluding known invalid top/border rows if proven by
  diagnostic output.
- Record the valid-pixel policy and source artifact in both the raw sweep HDF5
  and `camera_params_psf_safe.json`.
- Keep `allow_full_scale_pixel=False` and `allow_non_finite_pixel=False` within
  the valid domain.
- Add tests proving that excluded invalid pixels do not affect PSF safety,
  while full-scale pixels inside the valid domain still fail.

## Acceptance Criteria

- Phase 3.0.5b no longer treats documented invalid top-row artifacts as PSF
  saturation.
- The valid-pixel domain is recorded in HDF5 and JSON provenance.
- The strict all-valid-pixels rule remains enforced.
- Hardware probe evidence is preserved or converted into a reproducible
  diagnostic script.
- Documentation states that full-frame strict mode is valid only if all camera
  pixels are known valid imaging pixels.

## Open Questions

- Should the first implementation be a fixed top-row/border exclusion, or a
  generated bad-pixel/valid-pixel mask?
- Should this be Phase 3.0.5b blocking before any canonical
  `camera_params_psf_safe.json`, or an explicit hardware waiver path?
- Should we add a diagnostic script under `scripts/` to reproduce the
  shutter/gain artifact probe instead of keeping local output files only?
